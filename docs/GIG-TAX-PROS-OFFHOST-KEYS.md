# Client access and separate firm recovery — active requirement

Luke requires sensitive tax records, SSNs/identifiers and documents to remain
unreadable after compromise of the hosting/storage service. He confirmed client
access plus a separate firm master recovery key kept off that hosting service.
He also requires every iOS feature to have its durable state represented in
the shared backend and appropriate website views, rather than syncing only
trips, income and expenses. These requirements supersede the earlier
server-key-encrypted-file design.

## Required trust boundary

The storage/API host receives ciphertext and minimal opaque routing/revision
metadata. It must not hold client, firm-recovery or firm-signing private keys,
and must not obtain plaintext during upload, download, ingestion, calculation,
search or rendering. Public recipient keys alone do not grant decryption.

Decryption and views run on signed native clients or a separately controlled
trusted frontend. The current server-rendered customer/staff HTML cannot be
treated as that trusted frontend: compromised HTML/JavaScript could steal keys
or plaintext at unlock. Static `gigtax.pro` distribution must remain under a
different deployment/security boundary from a future ciphertext API host.
Clients independently pin the firm signer/recovery public keys; replacing an
API configuration file must not substitute an attacker's recipient keys.

The recovery key's private portion belongs on a separate trusted firm device
or offline recovery medium, with a protected recovery procedure. A folder,
environment variable or `vault.key` on the same host is not this separation.
The current local Node backend runs on Luke's Mac, so storing a production
master beside that service in that Mac's files is not off-host protection.
No real master or signing private key has been generated by this work.

## Implemented foundation, not yet an activated product

- Actual CryptoKit and browser WebCrypto envelope primitives use independent
  client and firm-recovery key slots and authenticated account/object/context.
  HPKE is the RFC9180 P256/SHA256/AES256GCM suite; each object has a fresh
  AES256GCM data key and each recipient has a fresh HPKE sender context.
- A signed public enrollment manifest binds workspace/account/client, recipient
  keys, expiry and a monotonic epoch. The firm signer is separate from the
  recovery key. Backend configuration contains public pins only; clients must
  independently verify those same pins and the manifest.
- A separate opaque encrypted-object API rejects plaintext aliases/filenames,
  unknown fields, wrong account/context/recipients and unsupported versions.
  It enforces revisions/idempotency and content-free sync tombstones.
- Explicit enrollment guards reject known legacy plaintext tax/record/receipt/
  document writes and host-side provider authorization/sync for that account
  and linked-client scope. Provider disconnect/revocation remains available.
  Client preflight and persisted enrollment must stop legacy sends *before*
  network transmission; rejecting a body after receipt is not host blindness.
- Purge removes a current encrypted object and its object-specific mutation
  cache. It does not establish removal of old plaintext, provider copies,
  recipients' downloads, database free pages, exports or retained backups.

The prototype v1 primitives were checkpointed at `ac8f001`. The current v2 path
uses standard HPKE Auth mode with a trusted author key and rejects base/v1
envelopes. Complete ordered recipient wraps are additionally bound to content
authentication, so tampering with an unused recovery slot is detected during
client decryption. Actual CryptoKit/WebCrypto interoperability and offline
synthetic firm-key signing/recovery have passed. This is not public
nonrepudiation or rollback-proof
history, and does not survive theft of the relevant endpoint private keys.
Signed/history anchoring, device key custody and recovery workflows remain
separate acceptance gates.

The offline firm library/CLI in `packages/secure-tax-client` creates encrypted
key bundles, signs independently verified client enrollment requests and
recovers explicitly selected encrypted objects. Commands require an off-host
acknowledgment, passphrases through a file descriptor and exclusively created
private outputs. These are implemented tools, not evidence of real off-host key
custody or a completed recovery drill. Real keys and public pins remain absent.
Native setup stages public enrollment approvals and deliberately cannot activate
legacy write guards until the encrypted synchronization path is complete.

The native Account screen now connects explicit protected Journal archive
upload/list/preview/import-review/delete, with bounded versioned payloads,
account binding, exact retry ciphertext and revision checks. All30 committed
Journal fields from native9cfa62e are represented; separate route/receipt files
and uncommitted reputation work are not. Independently bundled workspace pins
stop legacy native mutations before networking, even before API enrollment.
The trusted static browser has corresponding decrypted views and ordinary forms,
with client-only keys, encrypted backup and memory-only sessions. Snapshot
views are read-only; separate web edits do not automatically merge with the phone.

Legacy coach writes now fail before body parsing, before/after optional Peel
work and inside the final transaction when encryption is required. Existing
coach rows and other retained plaintext are reported as unresolved exposure.
The offline copied-backup exporter supports records/linked receipts/submitted
documents only; it never uploads or erases original data. These implemented
paths have synthetic verification and app compilation, not live account
activation, actual physical key custody or full multi-view feature acceptance.

## Migration and feature coverage

Read-only encrypted staff access is now implemented using detached, signed
per-device grants and per-object key capsules. Original v2 client envelopes and
their client/recovery recipients remain unchanged. The separately distributed
staff UI requires actual MFA, independent pins and a local staff key. A compiled
synthetic pilot verifies record/document decryption, encrypted device-backup
import, replacement-device recovery through a new CLI process, signed revocation,
fresh-revision denial and clean restore. It does not establish physical key
separation, real browser persistence or public TLS. See the
[staff contract](SECURE-TAX-STAFF-CONTRACT.md) and
[verification](verification/encrypted-staff-20261107.json).

The [AWS key-service package](SECURE-TAX-AWS-KEY-SERVER.md) requires a different
AWS account from the data host, a strict MFA operator and private KMS/S3 custody.
Its reviewed local artifact and synthetic provider tests are preparation only:
saved AWS credentials return InvalidClientTokenId. No cloud resources or real
firm keys have been created. AWS provider controls do not certify this application.

The current plaintext journal, raw receipt files, generic SDK tax fields,
audit/command snapshots, mutation results, profile data, provider source facts,
legacy JSON, client caches, exports and existing backups require an explicit
migration/removal plan. Old backups include the old server vault key.
Encrypting a new copy does not retroactively protect an older readable copy.
Do not automatically destroy old work: first verify client access and actual
firm recovery of the new encrypted copies, then remove known legacy copies
under an explicit retention/removal policy and expose remaining exposure.

The current provider adapters hold credentials that can fetch plaintext data
from Plaid/Uber. A compromised host could use those credentials regardless of
later file encryption. Protected live ingestion therefore requires an off-host
trusted broker/client or another authorized provider model. Do not activate
those adapters as satisfying this boundary. Credentials, provider approval,
individual consent and supported-provider API limits still apply.

Full feature inventory and web/sync gaps are tracked in
[`GIG-TAX-PROS-SECURE-FEATURE-PARITY.md`](GIG-TAX-PROS-SECURE-FEATURE-PARITY.md).
Durable goals, planning/reserves, offers, decisions/work, reminders, bank review,
routes and tax/profile/document state all need encrypted sync and usable
authorized web views. Transient screen frames, rejected sensor fixes and
device permission grants need not be retained or turned into server controls.
Do not present sample data or a new encrypted-object API as proof of this parity.

## Unfinished acceptance

Real off-host recovery setup and protected backup, trusted frontend/key distribution,
staff/device activation, encrypted staff editing/review, native/browser secure
synchronization, migration/erasure, all feature views and actual end-to-end
hosted/phone acceptance remain open.
Public client hosting is still unconfigured. Keep the overall goal active.

The application/key workflows have not received an independent security review.
Browser dependency `@hpke/core`1.10.0 is pinned after checking the
[published patched-version advisory](https://github.com/dajiaji/hpke-js/security/advisories/GHSA-73g8-5h73-26h4);
the [library does not claim a formal audit](https://github.com/dajiaji/hpke-js#readme).
Protocol reference: [RFC9180](https://www.rfc-editor.org/rfc/rfc9180).
